# F-03：Annex B 工作簿是用 `USL[12][4]` = 0.22 產生的

> 對照／Pair: [English](report.en.md) · 來源：zh · 同步 2026-11-05

Claude（Opus 5.5，主代理，非 Astra），2026-11-05 Asia/Taipei。對照：`v0.4.0` = `118322f`。延續 [`2026-11-05-annexb-bias-118322f/`](../2026-11-05-annexb-bias-118322f/report.md) 與 [`2026-11-05-zwst-root-cause-118322f/`](../2026-11-05-zwst-root-cause-118322f/report.md)。

## 結論

- **SQAT v2.0 不能當作 0.24 的佐證。** 它跟 MoSQITo 一樣是實作，不是標準本身；v2.0 那一格仍是 0.24（tag `v2.0` = `94f489c`，第 519 行），但 v2.0 的版本說明和 PR #48／#49 都沒有提到 Table A.9 或 `USL`。它宣稱「貼近 Annex A C 程式」，這一格卻跟 C 程式不同，所以這個宣稱反而說明了 SQAT 沒有逐格對齊 C 程式。SQAT 跟 MoSQITo 是否彼此獨立也無法確認。
- **濾波器的根因跟 0.24 無關。** 前端誤差和換算慣例影響的是頻帶位準，`USL` 是 slope 階段的上側斜率表，兩者互不相干。不過前兩輪查出這兩個原因後，我們能把工作簿重現到 1e-4 sone，於是第一次可以直接檢驗工作簿當初用的是哪個值。
- **檢驗結果：ISO 532-1 隨附的 Annex B 工作簿，是用官方 Annex A C 程式（`USL[12][4]` = 0.22f）、以「滿刻度 1.0 = 2√2 Pa」換算產生的。**
  - 用未修改的官方 C 程式跑 2√2 換算的輸入：穩態訊號 2–4 的 N 完全相同（訊號 5 差 0.0001），四個穩態訊號的 240 格比響度全部完全相同；時變訊號每一點的誤差都 ≤ 0.0001，也就是四捨五入的誤差。
  - 同一份 C 程式只把這一格改成 0.24f：在兩版差距 ≥ 2e-4 sone 的 12,287 個點上（12 個訊號），工作簿跟 0.22 版完全相同的有 **11,174** 點，跟 0.24 版完全相同的是 **0** 點；比較接近 0.22 版的佔 12,109 點（98.6%）。
- **所以，0.24 跟標準自己的參考數據不一致；0.22 則跟標準隨附的兩個可執行產物（C 程式和工作簿）都一致。** 在 Annex B 的 5% 容差下，兩個值都會通過，這也是先前 F-03 測不出差別的原因。
- **還不能說 0.22 就是更正後 Table A.9 的正式值。** Table A.9 的原文仍未取得；這份 C 附件帶有 ISO_DIS／2016 的標記，2017-11 的更正內容未知。理論上仍可能是「更正把印刷表改成 0.24，但附件沒有跟著更新」。不過那樣的話，標準的印刷表會跟它自己的參考程式和參考數據互相矛盾，可能性明顯較低。這是推論。

## 1. 方法

1. [make_float_wavs.py](make_float_wavs.py)：把 Annex B 訊號 2–25 換算成 `int16 / 32768 × 2√2` Pa，存成 32 位元浮點 WAV（官方 CLI 讀浮點 WAV 時不需要校準檔）。
2. 從官方原始碼建兩支 CLI（MSVC x64，`/O2 /fp:precise`，[build-v022.cmd.txt](build-v022.cmd.txt)、[build-v024.cmd.txt](build-v024.cmd.txt)）：
   - `v022`：完全不改，`ISO_532-1.c` 的 SHA-256 為 `a74b45ed…`。
   - `v024`：只把 `USL[12][4]` 從 0.22f 改成 0.24f，跟 `tools/golden-c-usl12-4.diff` 相同，SHA-256 為 `739af24d…`。這兩個 hash 都跟 0.4.0 release 紀錄登記的一致。
   - 對照組：新建的 `v022` 在全部 24 個訊號上的 `Loudness.csv` 和 `SpecLoudness.csv`，跟先前輪次的 `reference_cli.exe` 逐位元相同。
3. [run_two_cli.py](run_two_cli.py)：兩支 CLI 各跑一次（穩態訊號 2–5 用 time skip 0.2 s；時變訊號 6–25，訊號 15 用 diffuse field），輸出（小數第四位）逐點跟工作簿比對。
4. [decisive_points.py](decisive_points.py)：只取兩版差距 ≥ 2e-4 sone 的點。這個差距超出小數第四位四捨五入能造成的範圍，所以這些點上「工作簿等於哪一版」可以判斷它是由哪一版產生的。
5. [compare.py](compare.py)：另外用 0.4.0 wheel（Rust，0.24）跑同樣的輸入，作為旁證。

## 2. 結果

### 2.1 全部點（[two-cli-compare.json](two-cli-compare.json)）

- 共 49,675 個比對點，兩版在小數第四位不同的有 15,801 點：工作簿等於 0.22 版的 14,277 點、等於 0.24 版的 411 點、兩者都不等的 1,113 點。
- 等於 0.24 版的那 411 點，兩版都只差最後一位，落在四捨五入的邊界上；所以只看這一層無法判斷，要看 §2.2。
- `v022` 對工作簿的最大差：每個訊號都 ≤ 0.0001。`v024` 最大到 0.0169（訊號 6）。

### 2.3 旁證：Rust 0.4.0（0.24）

[compare.json](compare.json)：在 Rust 跟 0.22 版 C 差距 ≥ 2e-4 的點上，工作簿每一點都比較接近 C（例如訊號 14 是 3,623／3,623，訊號 15 是 5,151／5,151），沒有任何一點等於 Rust。這跟 §2.2 的結果一致，表示 Rust 和 0.22 版 C 之間的差異，確實來自這一格。

## 3. 對 F-03 的意義

| 先前的結論 | 現在 |
|---|---|
| Annex B 無法分辨 0.22 和 0.24（5% 容差） | 容差判定仍然一樣；但在 1e-4 sone 的精度下，工作簿只跟 0.22 一致 |
| 0.22 的一手來源：官方 C 附件、1991 BASIC 原刊、MetaSona | 再加上 Annex B 工作簿，而且它就是 C 附件跑出來的 |
| 0.24 的來源：MoSQITo、SQAT（v1.0／v1.3／main） | 再加上 SQAT v2.0；依然都是實作，沒有任何標準來源 |
| Table A.9 更正內容未知 | 仍然未知 |

## 4. 選項（需要決定）

| 選項 | 內容 | 影響 |
|---|---|---|
| **A（建議）**：改成 0.22 | 跟官方 C 程式和工作簿一致；C golden 可以直接用未修改的官方程式產生，不再需要「一格例外」 | 數值變更；可以跟 ZWST 前端一起放進 0.5.0；跟 MoSQITo 的差距會在受影響的點上增加最多約 0.017 sone |
| B：維持 0.24 | 維持 MoSQITo／SQAT 相容 | 要在文件寫明：跟標準自己的參考數據在約 1.2 萬個點上不一致，最多差 0.0169 sone |
| C：先取得 Table A.9 原文再決定 | 購買 corrected 2017-11 版標準 | 唯一能關閉權威門檻的方法；不影響 A 或 B 的數據 |

D3（2026-11-03）把 0.24 列為「暫定」，條件是「日後若原文證實 0.22」。現在的新證據不是原文，而是標準隨附的參考數據；能不能把它當作改值的依據，需要你判斷。我的評估是：證據的分量已經明顯偏向 0.22，而且改成 0.22 之後，「與 Annex A 一致」就不再需要任何例外，CITATION 也能寫得更乾淨。

## 5. 限制

- 工作簿和 C 附件來自同一個保存檔（`tmp/c01-material/official/`），附件的版本（ISO_DIS／2016 標記）跟 2017-11 更正版的關係仍未確定。
- 只比對時變的 N(t) 和穩態的 N、N′；時變訊號 6–13 工作簿裡那條 N′(t) 沒有逐點比對 0.22／0.24 兩版。
- 浮點 WAV 是 float32，跟原始 int16 路徑可能有 1e-7 等級的差異，對小數第四位的判定沒有影響。
