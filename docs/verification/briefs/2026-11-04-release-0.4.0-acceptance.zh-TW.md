## 1. 問題

本機 `main` 上的 commit `fca4ccd`（`fca4ccda18a8fbada77031425e5e683f1acd5a8d`，「docs(release): record F-07 …」）尚未推送、未打 tag、未跑 CI。它是 0.4.0 的候選快照，由 Claude Opus 5.5 分兩輪實作（Round 1 `93ba5e4`…`2fc1708`，Round 2 `a1a261d`…`fca4ccd`），主代理（Claude Fable 5.1）已做兩輪驗證。本次發布宣稱：

- **D1。** 正確性參考由 MoSQITo 1.2.1 改為 ISO 532-1:2017 Annex A 的官方 C 程式；MoSQITo 降為相容性對照（總響度 5e-3 sone），比響度對 MoSQITo 只記錄。
- **F-04。** `calc_slopes` 不再每幀把總響度捨入到 0.001／0.01 sone。
- **F-05。** 斜率段在 band 最後一個 0.1 Bark 格啟動且在 ZUP 前碰到核心響度時，band 依 Annex A 補完到 ZUP，下一 band 從 ZUP 起算。
- **F-06。** 公開 `core::calc_slopes*` 的 band 0 不再經 `prev_grid_index(0) = 239` 讀 band 20。
- **F-07。** 比響度在「斜率段於取樣位置之前結束」的格，寫包含取樣位置那一段的值（後續斜率段或核心值），不再外插；總響度逐位元不受 F-07 影響。
- **C golden（D4 修訂）。** 以官方 `ISO_532-1.c`（SHA-256 `a74b45ed297cd09ac60701a923120341137d227e536f3109ae4ece810d834491`）只替換 `USL[12][4]` 的 `0.22f` 為 `0.24f` 產生；門檻三層：C-01 四個尾點總響度與比響度 1e-10；全序列總響度 1e-4 sone；全序列比響度 3e-4 sone/Bark。全序列殘差宣稱完全來自 C 程式自身的 `_ZUP += .0001f` 與 float32 常數。
- **不變。** API、輸出格線（`ceil(ceil(L/24)/4)`）、串流契約（批次＝串流逐位元）、SIMD 分派、C ABI、Python shape、Annex B 判定均不變；`USL[12][4]` 維持 0.24。
- **hash。** `tests/hash_gate.rs` 的 `n` 自 Round 1 起逐平台重凍、`n_specific` 自 Round 2 重凍、`time_axis` 不變；`n` 在 Round 2 前後不變（F-07 不動總響度的證據）。

請獨立判定每項宣稱在凍結 commit 上是否成立，以及是否有任何事項阻擋推送與打 tag。

## 2. 範圍

1. **凍結。** 記錄完整與短 commit、`git status --porcelain`、受驗來源 hash。從 `fca4ccd` 的隔離 checkout（`git worktree add` 或 `git archive`）建置；不要用主工作樹。記錄工具鏈（rustc、cargo、Python、NumPy、maturin、MSVC）。
2. **C golden 可重現。** `data/golden-c/` 已 gitignore，你必須自己產生：`python tools/gen_golden_c.py`（參數見其 docstring；官方 C 與 header 在 `tmp/c01-tail-root-cause-aa379db-run2/c/`，ISO 原始檔在 `tmp/c01-material/official/`，MSVC 的 `vcvars64.bat` 用本機安裝）。先驗證官方 C 的 SHA-256 等於上列值；確認工具套用的 diff 與 `tools/golden-c-usl12-4.diff` 一致、替換版 SHA-256 為 `739af24dee118027cb419fcdb051d8b56b274211d986140d66d7ff4b9d52a7e9`；把產生的每個資料檔 hash 與 `tools/golden-c.sha256` 逐檔比較（宣稱資料檔逐位元可重現，只有 `meta.json` 日期不同）。給錯 `--official` 時工具須以 hash 不符退出。
3. **重跑 gate。** `cargo fmt --all -- --check`；`cargo clippy --workspace --all-targets -- -D warnings`；`iso532-ffi` 的 `--all-features` clippy；`cargo test --workspace --no-fail-fast`（記錄數量，與 release 紀錄的 146／0／3 ignored 比較）；`cargo test -p iso532 --test golden_c`、`--test hash_gate`、`--test output_grid`、`--test stream`、`--test annexb`、`--test annexb_validator`；`python tools/doc_pairs.py --check`；`python tools/redact_paths.py --check docs`；`maturin build --release` 後在全新 venv 安裝 wheel，`ISO532_REQUIRE_PARITY=1` 跑 `pytest iso532-py/tests`（紀錄宣稱 87 passed、0 xfailed）。差異是發現，不自動視為失敗。
4. **以獨立 harness 驗 F-04／F-05／F-06／F-07 對官方 C。** 自寫 wrapper（C 或 ctypes）呼叫未修改官方 C 的 `f_calc_slopes` 與 `f_loudness_from_signal`，以及只換一格 0.24f 的版本；自寫 Rust 程式以 path 依賴 `iso532` 取 `core::calc_slopes` 與 `loudness_zwtv`。至少涵蓋：
   - 單幀：訊號 18 第 1564 幀（NL 向量在 `iso532/src/core/calc_slopes.rs` 的 `SIG18_FRAME1564`；或自己從 pipeline 取）cell 36 等於 `nm[4]`、cell 35 在第一段內；訊號 23 第 3893 幀總響度 4.7508434035893385（容差 1e-12）；`nm = [0; 21], nm[20] = 1` 總響度 0.4、band 0 比響度全 0。
   - 整段：對 Annex B 訊號 18／23／24／25 與九個 golden 訊號，逐幀比較 Rust 對 0.24f 版 C 的總響度與比響度最大差，與 release 紀錄的表（總響度 ≤2.712e-5、比響度 ≤2.100e-4）比較；C-01 四個尾點總響度差 ≤9.0e-11、比響度 ≤3.3e-23；對未修改 C 的尾點差 −1.43e-8／−1.28e-7／−9.33e-9／−7.41e-11。
   - **總響度不受 F-07 影響。** 並列建置 `2fc1708`（Round 1 末）與 `fca4ccd`，對所有 Annex B WAV 與 3 s contract signal 位元比較 `n` 與 `time_axis`（宣稱逐位元相同）；`n_specific` 差異只應出現在斜率段結束於格內的那些格，回報首個差異座標與數量。
5. **殘差歸因（診斷，不是驗收門檻）。** 以官方 C 另建 `_ZUP += .0001f` 改 0、表格與常數改 binary64 的診斷版（先前輪次有 `epsilon_zero_tables_double.diff.txt` 可參考），量 Rust 對它的逐幀總響度與比響度最大差；宣稱總響度 ≤1.5e-14。若比響度仍有殘差，回報其量級與位置（C 的 `ZK += 0.1f` 累加是已知的另一個 float32 來源），寫「發現」。
6. **契約不變。** 自訂 chunk 序列（含 1 個樣本與大於 96 的 chunk）餵至少三個 Annex B 訊號，串流與批次的 `n`、`n_specific`、`time_axis` 位元比較；`zwtv_out_frames` 對 `L ∈ {4800, 4801, 4823, 4824, 4825, 47999, 48000}` 等於 `ceil(ceil(L/24)/4)`；`iso532-ffi/include/iso532.h` 與 `v0.3.1` 的 header 逐位元相同；DLL 匯出符號與 `v0.3.1` 相同；Annex B 全部 ISO 參考點在 0.4.0 與 `v0.3.1` 的通過數相同，回報最小餘裕。
7. **hash gate。** 在你的機器上 `HASH_GATE_DUMP_ONLY=1 cargo test --test hash_gate -- --nocapture` 取 dump，與 `tests/hash_gate.rs` 常數比較；Windows 的 `n`／`n_specific` 允許因 CPU／UCRT 不同而異（寫清楚差在哪、`time_axis` 必須相同）；若有 Linux（容器亦可），`n`、`n_specific`、`time_axis` 應與 linux 常數相同。Python `test_smoke.py` 的 N hash 同樣處理。
8. **MoSQITo 相容性。** `golden_zwtv`／`golden_zwst`／Python parity 的總響度對 MoSQITo golden ≤5e-3 sone；比響度對 MoSQITo 的記錄值（時變最大 3.147e-2，annexb_sig5；穩態 7.960e-3）可重現。
9. **紀錄一致性。** `iso532`、`iso532-ffi`、`iso532-py` 的 `Cargo.toml` 與 `Cargo.lock` 為 0.4.0；`CITATION.cff` 仍 0.3.1（紀錄已說明，不是缺陷）；`CHANGELOG.md` 0.4.0 段列 F-04～F-07 與 golden 基準變更；`docs/RELEASE-0.4.0-2026-11-04.zh-TW.md` 的 commit 表與 `git log 5cb036a..fca4ccd` 相符；紀錄「驗證」與「C golden」兩節的每個數字與你的量測比較；CI 檔 `.github/workflows/ci.yml` 的 py job 有 `HASH_GATE_DUMP_ONLY`。
