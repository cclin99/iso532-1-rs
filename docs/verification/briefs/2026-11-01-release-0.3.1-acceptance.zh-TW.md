# 驗證交辦簡報：0.3.1 發布前的獨立驗收

> 對照／Pair: [English](2026-11-01-release-0.3.1-acceptance.md) · 來源：zh · 同步 2026-11-01

對象：Astra（`gpt-6-astra`）。2026-11-01（Asia/Taipei）由主代理依使用者決定「先讓 Astra 獨立驗證」發出。驗收輪；不改程式。tag `v0.3.1` 在本輪交付前不打。

## 1. 問題

Release commit `30e4279`（`30e427963da88db8b23e82cf612f047f36cd164b`，「release: 0.3.1」）已推上 `main`，CI run 41278186406 全綠，產出物已建置並在 `docs/RELEASE-0.3.1-2026-11-01.zh-TW.md` 記錄 hash，tag 尚未建立。本次發布宣稱：

- C-02：批次函式以 `Iso532Error::NonFiniteInput { idx }`（錯誤碼 4、`ISO532_ERR_NONFINITE_INPUT`、Python `ValueError`）拒絕 NaN／±Inf 樣本；串流路徑不變。
- C-01：輸出格線 `frames = ceil(ceil(L/24)/4)` 凍結為契約；第 `j` 點恰在 `96j/48000` 秒，值只取決於 samples `≤ 96j`。
- V-01：測試使用的 Annex B 驗證器採工作簿規則 `max(0.1, 0.05·|ref|)`，對無效資料 fail-closed。
- 對有限輸入，與 `v0.3.0` 相比沒有任何數值輸出改變。

請獨立判定每項宣稱在凍結 commit 上是否成立，以及是否有任何事項阻擋打 tag。

## 2. 範圍

1. **凍結。** 記錄完整與短 commit、`git status --porcelain` 與受驗來源 hash。從 `30e4279` 的隔離 checkout（`git worktree add` 或 `git archive`）建置，不要用其他代理會修改的共用工作樹。記錄工具鏈版本（rustc、cargo、Python、NumPy、maturin、C 編譯器）。
2. **重跑 gate。** `cargo fmt --all --check`；在 `iso532/` 執行 `cargo clippy --all-targets -- -D warnings` 及 `cargo clippy --workspace --all-features --all-targets -- -D warnings`；`REQUIRE_AVX2=1 cargo test --workspace --all-features`；`python tools/golden_manifest.py --verify`；`maturin develop --release` 後以 `ISO532_REQUIRE_PARITY=1` 跑 `pytest iso532-py/tests`；`python tools/doc_pairs.py --check`；`python tools/redact_paths.py --check docs`。記錄數量並與 release 紀錄比較（138／0／3 ignored；175 檔；pytest 69）。有差異是發現，不自動視為失敗；寫清楚差在哪。
3. **以獨立 harness 驗 C-02**（不是只跑庫內測試）：自寫 Rust 程式以 path 依賴 `iso532` 與 `iso532-ffi`；自寫 C 程式對 `iso532-ffi/include/iso532.h` 與該 commit 建置的共用庫；自寫 Python 腳本對步驟 2 建出的 wheel。對 `loudness_zwst` 與 `loudness_zwtv`：NaN、+Inf、−Inf 各放頭、中、尾；同時放兩個非有限樣本時 `idx` 須等於第一個；檢查順序（取樣率錯加 NaN → 取樣率錯誤；太短加 NaN → 長度錯誤）；次正規數、±0.0、1e300 不被有限性檢查拒絕（1e300 可能回 `LevelExceeds120dB`；記錄實際回什麼）。C ABI：輸出緩衝區預填哨兵值，確認回傳 4 且緩衝區不動；確認 header 常數等於 4 且等於 `Iso532Error::NonFiniteInput { .. }.code()`。串流：NaN 樣本歸零、下一輸出幀帶 `NONFINITE_INPUT`、`flush` 後仍回報該 flag，且數值輸出與在同位置餵 `0.0` 的串流位元相同。Python：`ValueError` 訊息含 index。
4. **以獨立 harness 驗 C-01。** 對 `L ∈ {4800, 4801, 4823, 4824, 4825, 4895, 4896, 4897, 24013, 47905, 47916, 47927, 47928, 47952, 47999, 48000}` 自行計算 `ceil(ceil(L/24)/4)`，與 `zwtv_out_frames`、`iso532_zwtv_out_frames`、Rust 結果長度（`n`、`time_axis`、`n_specific = 240·frames`）及 Python 陣列形狀比較。確認 `time_axis[j].to_bits() == ((96*j) as f64 / 48000.0).to_bits()`。真實訊號的前綴決定性：至少三個 Annex B WAV，在非 96 倍數的長度截斷，把短結果的每一點與完整結果同一點位元比較（`n`、`time_axis`、全部 240 個 Bark 列）。串流：以自訂的 chunk 序列（含 1 個樣本的 chunk 與大於 96 的 chunk）餵一個 Annex B 訊號，與批次結果比較點數與數值。本輪不重做補零官方 C 參考值；那是另一份簡報 `2026-11-01-C01-zero-pad-reference.zh-TW.md`。
5. **V-01 驗證器。** 自固定快照，以自己的測試二進位呼叫 `iso532/tests/common/annexb_check.rs` 的 `annexb_verdict`／`annexb_tolerance`，施以 `docs/修正報告2.md` §11.5 與 §12.2 V-01 列的 fail-closed 控制（空向量、reference 或結果含 NaN／±Inf、shape 不符、放在 `data/` **之外**的損壞 CSV／bin 副本）。確認 `iso532/tests/annexb.rs` 確實經過驗證器、沒有繞過。驗證 `docs/V01-ANNEXB-VALIDATOR-2026-10-31.zh-TW.md` 的邊界陳述：binary64 下 `2.1 − 2.0` 大於 `0.1`，對 `ref = 2.0` 以 `2.0625` 通過、`2.125` 失敗；回報全部曲線中最小的真實 Annex B 餘裕 `tolerance − |got − ref|`（紀錄宣稱 ≥ 0.0851 sone/Bark）。
6. **有限輸入無數值改變。** 並列建置 `v0.3.0`（把 tag 解析成 commit 並記錄）與 `30e4279`。對每個 Annex B WAV 及 `tools/compare_mosqito.py` 使用的 3 s contract signal，在兩個建置上以預設初始化執行 `loudness_zwst` 與 `loudness_zwtv`，位元比較 `n`、`time_axis`、`n_specific`；回報數量與首個差異座標（若有）。執行 hash gate dump（`cargo test --test hash_gate`，`HASH_GATE_DUMP_ONLY` 環境見 `.github/workflows`），與庫內凍結常數比較。
7. **產出物。** 主代理建置的檔案在 `<REPO>/tmp/dist-0.3.1/`（已 gitignore）。重新計算 SHA-256，與 release 紀錄表及 `SHA256SUMS.txt` 比較。`iso532.h` 與已提交的 `iso532-ffi/include/iso532.h` 逐位元比較。列出 DLL 匯出符號（例如 `dumpbin /exports` 或 `pefile`），與 `v0.3.0` DLL 的匯出比較（手上有就直接比，沒有就重建）；重建 `v0.3.0` 確認 import library 與其位元相同（紀錄宣稱與 `v0.2.0`、`v0.3.0` 相同）。在全新虛擬環境安裝 wheel、import、確認版本中繼資料為 0.3.1、批次函式遇 NaN 丟 `ValueError`。重建的 DLL 與 wheel 不期望與記錄 hash 逐位元相同（PE 建置中繼資料）；header 與 import library 應相同。
8. **紀錄一致性。** `iso532/Cargo.toml`、`iso532-ffi/Cargo.toml`、`iso532-py/Cargo.toml`、`Cargo.lock`、`CITATION.cff`（日期 2026-11-01）均為 0.3.1；`CHANGELOG.md` 的 `0.3.1 - 2026-11-01` 段列出 C-02、C-01、V-01；release 紀錄的 commit 表與 `git log v0.3.0..30e4279` 相符；CI run 41278186406 在 `30e4279` 上且六個 job 全部成功（`gh run view 41278186406`）。紀錄「驗證」節的每個數字都與你的量測比較。

範圍外：F-03；穩態前端；補零 C 參考值（另有簡報）；MoSQITo 時間量測（紀錄中的時間表是快照，不是驗收項）；防毒掃描（使用者手動步驟）；更改任何程式、golden 或測試。

## 3. 證據規則

- 每個數字都由交付資料夾內的腳本產生，且可由凍結 commit、記錄的工具鏈與 Annex B WAV hash 重現。harness 原始碼一併交付，與受驗來源分開記錄。
- 位元比較回報 `f64::to_bits`／`struct.pack` 十六進位，不用列印的十進位。
- §2 每一項分別回報 passed／failed／blocked／skipped／partial；缺口保留為缺口。歷史證據（0.3.0 各輪）不得補成 passed。
- 本輪不以 MoSQITo 為參考。與官方 C 程式或 release 紀錄的任何差異一律寫「發現／目前判斷」，不寫 bug。
- 不追蹤移動中的 `main`。若本輪期間 `main` 前進，受驗 commit 仍為 `30e4279`。

## 4. 交付

- 資料夾：`docs/verification/2026-11-01-release-0.3.1-30e4279/`；不得覆蓋舊資料夾。
- 檔案：`report.md`（繁體中文）與 `report.en.md`（英文），結構與數字相同；`results.json`（§2 每項：狀態、數量、首個差異座標、hash）；harness 原始碼與執行腳本；`delivery-check.md`；去識別化後產生、明確排除自身的 `delivery-integrity.json`。
- 交付前：`python tools/redact_paths.py <資料夾>` 再 `python tools/redact_paths.py --check <資料夾>`；把輸出（含 skipped 與警告）記在 `delivery-check.md`。逐檔盤點工具未涵蓋的副檔名與非 UTF-8 檔。資料夾內只放 UTF-8 文字檔；二進位、WAV 與 wheel 不進庫（只記 hash）。資料夾日後任何修改都須重做去識別化、檢查與 hash。原始輸入／binary／受驗來源 hash 保留原義，不冒稱去識別化副本與原檔位元相同。
- 結論用語：每項 PASS／FAIL／BLOCKED／SKIPPED／PARTIAL；整體 ACCEPT（沒有事項阻擋打 tag）、HOLD（列出阻擋項）或 PARTIAL（列出缺口並說明各缺口是否阻擋打 tag）。
- 交付不含 commit／push，也不建立 tag。主代理只 stage 交付資料夾、重跑去識別化檢查後提交；打 tag 前依 `report.en.md` 更新 release 紀錄的「獨立驗證」節。
