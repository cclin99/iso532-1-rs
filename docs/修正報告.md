## 3. F-01：低頻高音壓修正漏選最後一列

### 3.1 已確認原因

位置：`D:\ISO532\iso532\src\core\main_loudness.rs`，`main_loudness_unchecked`。

目前 `for range in 1..(DLL.len() - 1)` 僅處理第 1–6 列索引。當音壓超出已處理的門檻，先前設定的零修正可能保留下來，未使用第 7 列。

官方 C 則由第 0 列開始，逐列檢查 `level > RAP[row] - DLL[row][band]`，至最後一列為止。門檻相等時不向下跳列。

### 3.2 已重現反例

| 輸入 | Rust | 官方 C | 觀察 |
|---|---:|---:|---|
| 25 Hz 頻帶 118.000001 dB，其餘 27 頻帶 −60 dB | 154.93 sone | 52.514908816 sone | 相對差約 +195.02%；官方 CLI 輸出 52.51 |
| 2 秒、25 Hz、119 dB SPL 正弦波，stationary | 165.19 sone | 56.704172426 sone | 透過公開音訊 API 重現 |
| 同上，time-varying | 最大響度 172.131366877 | 最大響度 56.878693537 | 最大逐點差 115.538257456 sone；1,000 點中 866 點超限 |

注意：最後一列的「最大逐點差」不是兩個最大響度的直接相減。

337 組既有邊界／隨機掃描中，有 16 組總響度超限、30 組 specific loudness 曲線含超限點。這些是額外診斷案例，不屬於官方 Annex B。

### 3.3 擬議修正

採用有界的逐列選擇，規則與 Annex A 一致：

```text
row = 0
while row < last_row and level > RAP[row] - DLL[row][band]:
    row += 1
corrected_level = level + DLL[row][band]
```

此為設計描述，尚未寫入產品碼。

- 將完整範圍選取規則集中在共用核心，stationary、batch ZWTV、streaming 使用一致修正。
- 不改係數表、門檻比較方向、功率換算或後續積分。
- 保留既有有效範圍契約：批次低頻超過 120 dB 回傳錯誤；串流限幅並設定旗標。
- 不只把迴圈上限加一後就宣告完成；必須測量所有轉換邊界，尤其相等門檻。

### 3.4 回歸測試與接受條件

1. **選表層精確驗證**：11 個低頻頻帶、全部轉換門檻，各取相鄰可表示浮點值及門檻本身。有效範圍內選取的列索引與 DLL 值必須完全一致；超出 120 dB 的輸入則驗證既有拒絕／限幅契約。
2. **核心反例**：118.000001 dB 案例必須採第 7 列的 −15 dB 修正。預期修正後響度接近 C；最終結果可能因 Rust 現有取整與其他已知差異而不逐位元相同。
3. **端到端反例**：25 Hz／119 dB 合成音的 stationary 與 time-varying 必須通過嚴格幅度容差。校準、取樣率、長度及 C TimeSkip 與原反例保持一致。
4. **337 組重跑**：保留修正前後逐案結果。不能預設所有失敗都由 F-01 造成；剩餘超限必須定位原因，未釐清則仍為 PARTIAL。
5. **傳播路徑**：free／diffuse、scalar／AVX2、Rayon／Sequential、批次／串流限幅路徑均須涵蓋。

## 4. F-02：批次非線性衰減使用未來尾端初始化

### 4.1 已確認原因

位置：`D:\ISO532\iso532\src\zwtv\nonlinear_decay.rs`。

- scalar：`NlBandState::mosqito_seed(row[n_time - 1])`。
- AVX2：載入最後 frame，傳入 `NlGroupState::mosqito_seed`。
- 官方 C 每個頻帶的 `UoLast`、`U2Last` 均從零開始。
- 目前串流路徑已使用零值狀態，因此此次問題不能直接擴張成「streaming 也有相同非因果初始化」。

### 4.2 已重現反例

兩個一秒訊號的前 0.5 秒完全相同且為零；其中一個後 0.5 秒保持零，另一個後 0.5 秒加入 1 kHz／80 dB tone。

| 檢查 | Rust batch | 官方 C |
|---|---:|---:|
| 前 0.25 秒輸出最大差 | 0.113550559256 sone | 0 |
| 加入未來 tone 後的第 0 點 | 0.001623810180 sone | 0 |

這證明保存的反例存在未來尾端對開頭的影響；尚未代表完整因果性已經形式化證明。

### 4.3 擬議修正

- batch scalar 初始化為 `NlBandState::default()` 所代表的零狀態。
- batch AVX2 初始化為 `NlGroupState::zero()`；尾端未滿四頻帶的處理也必須一致。
- 每次獨立批次重新初始化，防止 `ZwtvProcessor` 重用造成跨次污染。
- streaming 只在建立或 `reset` 時清零，不在每個 `push` 區塊清零。
- 保持 24 次內插、遞迴計算順序、輸出時間格線及原有延遲契約。
- 不將相鄰 frame 的必要內插前視誤認為本缺陷；測試需區分「輸出對應時間」與「該值可被送出的時間」。

### 4.4 回歸測試與接受條件

1. **未來尾端不變性**：相同前綴搭配靜音、音調、雜訊、不同長度尾端。在相同模式下，已確定且有共同定義的前段輸出須 bitwise 相同。最先凍結上述前 0.25 秒反例。
2. **靜音正確性**：反例前段的假響度應消失，與官方零輸出相符。禁止裁掉起始區間、增加 warm-up 或放寬容差來讓測試通過。
3. **低階狀態邊界**：空 frame 序列、單 frame、兩 frame、起始脈衝、持續音、最後 frame 非零，確認不越界且初始值正確。公開 API 的最短長度限制另測。
4. **processor 重用**：先算 A 再算 B，B 的結果應與新建 processor 計算 B 相同。
5. **batch／stream 對照**：在共同有效範圍、相同浮點環境與後端下，從起始時點逐點比較；不同切塊大小、reset／flush 均測。若不能 bitwise 相同，須先定位排程、浮點模式或算法差異，才制定有依據的數值門檻。
6. **保留既有串流契約**：延遲、旗標、warm-up 標記與跨區塊狀態不因批次修正而被意外改變。

## 6. 驗證程式本身的正確性

### 6.1 本輪新發現：有限值檢查不完整

對原腳本比較函式單獨施加負向輸入，結果如下：

| 負向案例 | 原函式結果 | 風險 |
|---|---|---|
| `metrics([NaN], [0])` | `strict_fail=0`，但 `nonfinite=1` | 只看失敗點數會誤判；原函式沒有統一的拒絕條件 |
| `envelope([0], NaN上下界...)` | `passed=true` | 只檢查 got 的有限值，未拒絕 NaN 參考上下界 |

本輪確認目前保存的 Rust／C 比較陣列均為有限值，所以這兩個負向案例**不直接推翻既有共同範圍的數值結果**。但原驗證工具尚不能作為會自動拒絕無效資料的完整驗收閘門。

### 6.2 擬議驗證工具接受條件

- 所有 got、reference、time、容許上下界均須有限，並拒絕空陣列。
- 形狀不一致不能被 `min(length)` 自動變成整體通過；共同範圍只產生診斷結果，長度狀態必須獨立。
- 要有明確 overall 狀態：PASS／FAIL／PARTIAL／BLOCKED，不能用程式成功結束或 `strict_fail=0` 代替驗收結果。
- 檢查 lower ≤ upper、嚴格與放寬範圍關係、時間單位與單調性。
- 工作簿缺列、無 cached 值、缺 specific 欄位、參考檔 checksum 不符，一律停止或列 BLOCKED。
- 對邊界判定加入負向控制：例如 reference=10、got=10.55 必須被 max 容差拒絕；正確區間內與剛超過區間都要測。
- 例外數按明確分母計算，處理不足 100 點、整除與非整除 1% 等邊界；不能跨不同訊號或 Bark 曲線混合分母掩蓋失敗。
- 保存每次執行的來源、編譯器、命令、返回碼與逐點結果。修正後資料不得覆蓋修正前證據。

本輪未修改原 `verify.py`；只新增外部複核腳本與結果。正式驗證工具改版也應先經審查。

## 8. Golden、相容性與回歸安排

兩項修正會有意改變數值；API 簽名維持不變也不代表結果完全相容。

- 先保存既有 golden／hash，不自動重新凍結。
- 以官方 C、選表規則及因果不變性建立新的正確性依據。
- 未受影響階段仍保持原先的精確回歸要求。
- 已知繼承舊初始化行為的 MoSQITo golden 保留為歷史比較，不以它否決有官方依據的改正，也不把差異全面忽略。
- 每一個變更的 hash 必須有歸因與對照數值，不能只用修正後 Rust 自己生成期望值。
- batch／stream 應從起始有效時點驗證，不能只使用「warm-up 之後接近」掩蓋起始問題。
- 專案測試、fmt／clippy、FFI 與 Python 契約、stream allocation／reset／chunk invariance，以及官方向量須分開列結果。

### 11.3 校準與既有專案 fixture 的差異

calibrated RMS = 0.019999999999999997 Pa

### 11.5 容差公式、例外計數與驗證器缺口

對工作簿有限、非負參考值 r，嚴格幅度界限為：

```text
d5 = max(0.1, 0.05 × r)
lower5 = max(0, r − d5), upper5 = r + d5
d10 = max(0.2, 0.10 × r)
lower10 = max(0, r − d10), upper10 = r + d10
```

時變界限再取本點與前後各一個 2 ms 時點的 lower 最小值、upper 最大值；首尾只使用存在的鄰點。這是逐時點的容許包絡，並不等同把整條曲線平移一次。部分末列公式引用下一空白列，按 Excel 的空白參照規則處理後，與只取存在鄰點的數值相同。

本次完成兩種互補檢查：

1. 不依公式字串，直接由參考數值重算全部 total／B.4 指定 Bark 的 5% 與 10% 原始界限、鄰點包絡和端點，共 575,288 格。
2. 使用受限公式解析器檢查工作簿實際 IF、AND、MINA、MAXA、SUM、COUNT、PERCENTILE 公式，對照 cached 值。共 720,122 式及 1,446 固定數值，沒有讀寫原 XLSX，也沒有用原檔的綠燈作 Rust 通過證據。

解析器不是完整 Excel 引擎；其範圍限於此次出現的公式。另直接讀取 XLSX 內 XML，保存 openpyxl 不支援的條件格式，避免忽略圖示門檻。

**恰好 1% 尚須裁定。** 工作簿分數為 `100×嚴格超限數/點數 + 放寬超限數`。條件格式把分數 `>=1` 切到下一圖示區間；原外部 `envelope` 卻採 `例外比例<=0.01`。因此恰好 1% 的顯示分類與程式接受條件並不一致。新控制測試明確採「至多 1%」作暫定規則，使用整數 `100×超限數<=點數` 避免比例捨入；**尚不能稱此閉區間已由完整正式標準確認**。目前實際向量超限數為 0，不受此差異影響。

### 11.6 N5 的三種定義必須分開

官方 CLI 對**整段已降採樣 total 輸出**計算 N5。helper 先排序，令 `j=int(0.95×n)`，取 zero-based `sorted[j−1]` 與 `sorted[j]` 的平均。Excel `PERCENTILE(...,0.95)` 則使用線性百分位，且通常先透過公式選擇排除靜音的列範圍。兩者不是同一個統計量。

### 13.3 各項錯誤如何影響 panel

**F-01 直接涉及 Track Meter 的共用核心。** 靜態呼叫鏈是：

```text
Track Meter process()
  → f32 音訊 × calibration_coefficient → f64 壓力
  → ZwtvStream.push()
  → main_loudness_clamped()
  → main_loudness_unchecked() 的低頻選表
  → StreamFrame.n → registry.last_n → Hub 顯示／排序／phon 推導
```

`main_loudness_clamped` 只將前 11 個 band 超過 120 dB 的值限制至 120；F-01 反例出現在 **118–119 dB**，所以限制到 120 不能排除這個錯誤。panel 的 Calibration 參數範圍是 74–134 dB；也不能僅因目前多以普通音量測試，就假設該輸入域不可到達。

這是**來源與呼叫路徑確認的影響**，本輪沒有重跑該 tag 的串流／CLAP 低頻 WAV，所以不把批次反例的 165.19 或 172.13 sone 冒稱為 panel 實測。P-01 必須取得實際串流與 plugin 端到端 red／green。

**F-02 不能直接宣判為 panel 的同一缺陷。** 批次使用 `mosqito_seed(last_frame)`；`ZwtvStream::new_nl_stage` 的 scalar 為 `NlBandState::default()`，AVX2 為 `NlGroupState::zero()`，兩者皆從零狀態開始。Track Meter 呼叫 stream，沒有呼叫這個批次尾幀 seed。因此：

- 目前確認的 F-02 是批次缺陷；沒有證據顯示 panel 有同樣的「讀取整段尾端後初始化」行為。
- 修正批次後仍須重驗 batch／stream 開頭、1 幀前視、reset／flush、時間索引及 warm-up 語意。舊的「等待 580 frames 再比對」不能替代從起始處核對。
- 若 panel 的 offline truth／測試 oracle 使用舊批次輸出，它的預期值可能需要重新歸因；不能單憑來源名稱就斷言每份 truth 都受影響，須逐一記錄產生路徑。

Hub 本身的音訊路徑是直通，不建立 `ZwtvStream`；它仍會顯示 Track Meter 傳來的錯誤 N，因此「GUI 沒有計算響度」不等於整體量測正確。N5 工作簿疑點目前不是已確認的 Hub 功能缺陷，仍主要影響驗收依據及未來若加入 N5 的設計。

### 13.5 Panel 專屬回歸與驗收

| 優先／ID | 回歸範圍 | 驗收條件 |
|---|---|---|
